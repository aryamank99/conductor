# Parallel conductors — one worktree each

**When to open this:** you're about to run (or are coordinating) more than one conductor session on a project. Part of the Conductor contract. Decision record: `plans/conductor-coordination.md` (do not rebuild the lease).

**Branch vs worktree:** the feature-branch discipline (branch off trunk → merge when GOAL passes) is general — it applies to *every* feature, solo or parallel (spine: "Branch hygiene"). The *worktree* below is the specialization for running conductors **concurrently**: it isolates the working directory so simultaneous agents can't clobber each other. Solo sequential work needs only the branch.

You can run more than one conductor session on a project, but **never two in the same working tree.** Each parallel conductor gets its own `git worktree` on its own branch — isolation by construction, so no shared-tree clobbering and no lock is needed. (Motivating incident: 2026-06-12, two conductor sessions on a client project interleaved writes in the same tree and a ~80-file commit landed mid-wiring; collision was avoided only by timing luck. A second worktree would have made it structurally impossible.)
- **Start a parallel conductor:** `git worktree add ../<repo>-<feature> -b <feature-branch>`, then open a Claude session in that directory. One worktree = one conductor = one branch.
- **Only run a second conductor on DISJOINT work** (different files/features). Same-feature parallelism is the Codex layer's job — one conductor dispatching multiple players on disjoint files. Two conductors are *only* for independent features; that constraint is also what keeps worktrees simple (see shared-artifacts caveat).
- **Integrate by merging to the main branch** once the feature's GOAL criteria pass and tests are green. If two branches are ready at once, **serialize the merges** — rebase each onto the current main branch and re-verify before it lands; never merge two divergent conductor branches against each other.
- **Awareness is manual:** `git worktree list` shows active peers; keep them on disjoint features and `git worktree remove` stale ones. (Automated peer/overlap detection, a shared plan registry, and a merge queue are deliberately NOT built — add them only if parallel runs become routine.)
- **Shared-artifacts caveat:** worktrees isolate *code* but also isolate `plans/`, ledgers, and CLAUDE.md/AGENTS.md across branches. That's fine while features are disjoint (neither conductor needs the other's plan, and they're not both editing the contract). If you do need a peer's plan, read it directly from that peer's worktree directory.
